## WooCommerce Pages (Phases 5–6)

**Phase 5 (WooCommerce Integration) — core plumbing done 2026-07-08.** Catalog is **dummy/placeholder data** — see the note at the end of this section for exactly where the admin edits it going forward.

**Phase 6 (Custom WooCommerce Design) — done 2026-07-08.** Every WooCommerce-rendered page now visually matches its mockup (re-themed to the canonical orange-gold palette where the source used the stale olive-gold set — Checkout). All template overrides live in `wp-content/themes/nia-theme/woocommerce/` (WooCommerce's own sanctioned override mechanism); Cart/Checkout stayed block-based per `ARCHITECTURE.md` §6 and were re-themed via CSS targeting WooCommerce Blocks' own stable class names plus direct edits to each page's block content (cross-sells heading, trust-row/microcopy content, native `showFormStepNumbers` step framing) rather than reimplementing the blocks.

**Real-browser verification (2026-07-08, later same day):** Shop archive + Product Detail Page were checked with an actual headless browser (Playwright/Chromium, installed to `/private/tmp/.../scratchpad/browser-check/` — not part of the repo, a throwaway verification tool) at mobile (390px) and desktop (1440px), after the client reported visibly broken layout from screenshots. This caught three real bugs curl/Store-API testing had missed, all now fixed:
1. A default WordPress "Shop sidebar" widget area (Search/Pages/Archives/Categories, from a fresh install's still-assigned default widgets) was rendering after the product grid and after Related Products — both WooCommerce's Shop archive and single-product templates call `do_action('woocommerce_sidebar')`, which this theme never uses. Fixed by unhooking `woocommerce_get_sidebar` (`Nia_Woocommerce::remove_woocommerce_sidebar()`).
2. WooCommerce's own default frontend stylesheets (`woocommerce.css`, `woocommerce-layout.css`, and especially the mobile-only `woocommerce-smallscreen.css`) were still loading alongside this theme's Tailwind stylesheet and fighting it with higher-specificity rules — product card badges/quick-add overlays lost their absolute positioning and collapsed into normal document flow, and card titles picked up a stray list-style bullet. Fixed via WooCommerce's own `woocommerce_enqueue_styles` filter (`functions.php`), which also then exposed that WC's default stylesheet had been the *only* source of the product grid's column layout — added `ul.products { grid ... }` to `input.css` to replace it (scoped to `ul.products` specifically, not a bare `.products` class, since WooCommerce's related-products wrapper section also carries a literal `products` class token that a bare selector would have wrongly matched too).
3. `woocommerce/single-product/related.php`'s item wrapper was a `<div>`, not a `<ul>` — `content-product.php`'s root `<li>` needs a real list ancestor to inherit `list-style: none` from, otherwise the browser's default stylesheet gives it its bullet back. Changed to a real `<ul class="products">`.

**Cart/Checkout real-browser verification (2026-07-21):** Playwright screenshots of Cart and Checkout (mobile + desktop, real populated line items via a real add-to-cart) found and fixed four selectors in `input.css` that didn't match WooCommerce Blocks' actual rendered markup — `.wc-block-cart-item` should be `.wc-block-cart-items__row`, `.wc-block-cart-item__product-name` should be `.wc-block-components-product-name`, `.wc-proceed-to-checkout .wc-block-cart__submit-button` never matched anything (no such wrapper exists — corrected to `.wc-block-cart__submit-button` directly), and the radio-control checked-state modifier is `__option-checked`, not `__option--checked-option`. Confirmed against the live DOM before and after the fix. All four pages — Shop, PDP, Cart, Checkout — are now real-browser verified.

**New gap noticed during the real-browser pass (not part of this fix, not yet actioned):** "Raw Seamoss — 200g," "Seamoss Powder — 250g," and "Seamoss Powder — 500g" render an empty placeholder box instead of a product photo on the Shop grid — those 3 dummy products appear to have no featured image assigned (a content/data gap, not a template bug; the other 5 dummy products display correctly).

**Where the admin manages the catalog day-to-day (no developer involvement needed):**
- **Products → Categories:** add/rename/delete/reorder categories, edit each category's thumbnail and description (the `taxonomy-terms-order` plugin, already active, adds drag-and-drop reordering here).
- **Products → All Products / Add New:** add/edit/delete products, set price (TZS — store base currency), stock, images, and mark/unmark the "Featured" checkbox in the Publish box (drives the homepage's Featured Products section automatically — see `ARCHITECTURE.md` §9a).
- **WooCommerce → Orders:** view/manage all customer orders (HPOS).
- **WooCommerce → Settings → Payments:** currently only "Cash on Delivery" is enabled as a placeholder — swapped for the real Selcom gateway in Phase 7.
- **WooCommerce → Settings → Shipping:** one placeholder flat-rate method ("Standard Delivery," 5,000 TZS, applies everywhere) — the client should confirm real shipping zones/rates before launch.
- All of the above requires zero code changes; this is the same "admin manages content, developer manages code" split already established for the Journal (blog posts) in Phase 4.
